# N400 Civics Test App — Design Spec

**Date:** 2026-05-13
**Status:** Approved — ready for implementation planning
**Target route:** `mannaos.com/n400app`
**Codebase location:** `apps/website/` (integrated, not standalone)

---

## 1. Problem & Goals

Help Vietnamese-American naturalization applicants prepare for the USCIS 2020/2025 civics test (128 questions, pass = 12/20 correct, fail = 9/20 wrong) through a bilingual, low-friction practice app.

**Primary user:** Vietnamese-speaking adults in Texas (Houston-area focus initially), low tech literacy, preparing for N-400 interview.

**Success criteria:**
- User completes signup + setup + first mock test in one session
- App usable by non-tech users — large fonts, big buttons, clear bilingual labels
- Mock test simulates USCIS interview rules accurately (stop early at 12 correct or 9 wrong)
- Audio pronunciation helps user prepare for English interview
- Lead generation channel for MOS N-400 filing service

**Non-goals (v1):**
- Paid plans / paywall
- Ads
- AI-generated content at runtime
- Email reminders for streak
- Mobile native app

---

## 2. Architecture Overview

**Integration model:** new routes inside existing `apps/website/` Next.js 16 App Router project. Reuse Supabase Auth, i18n (en/vi), admin pattern from Phase 3, layout shell.

**New routes (under `/[locale]/n400app/`):**
1. `/n400app` — landing + dashboard (auth-gated)
2. `/n400app/setup` — first-time location form
3. `/n400app/practice` — Daily Practice
4. `/n400app/mock-test` — Mock Test (interview simulation)
5. `/n400app/flashcards` — Flashcard mode
6. `/n400app/all-questions` — browse all 128

**Admin route:** `/[locale]/admin/n400` — content + location data management.

**Auth:** Supabase Auth (email + Google + Facebook OAuth). All `/n400app/*` routes except landing are auth-gated.

**Data:** Supabase Postgres (DB) + Supabase Storage (audio). Content in DB so admin can edit without redeploy. Aggressive Next.js cache (revalidate 1h + tag-based invalidation on admin edit) to keep page loads fast.

**External dependencies:**
- **Geocodio API** — street address → congressional district (Q29 lookup). Free tier 2,500/day. Address sent in-memory only, NOT persisted (see §3.2).
- **Upstash Redis** — IP/user rate limiting on Geocodio calls (§5.1). Provisioned via Vercel Marketplace.
- **Google Cloud TTS** (one-time generation): output stored in Supabase Storage with content-hashed filenames. Free tier 1M chars/month covers full ~1,300-file batch.

**Disclaimer (footer on all `/n400app/*`):**
> Tài liệu học liệu. Không phải tư vấn pháp lý. Nội dung lấy từ USCIS.gov.
> Study material only. Not legal advice. Content sourced from USCIS.gov.

## 3. Data Model

### 3.1 Content tables (admin-managed, public-read)

**`n400_questions`** (128 rows)
| field | type | notes |
|---|---|---|
| id | int PK | 1–128, matches USCIS numbering |
| category | text | e.g. "American Democracy", "System of Government" |
| question_en | text | |
| question_vi | text | |
| question_audio_url | text | Supabase Storage path |
| is_location_based | bool | true for Q23, 29, 61, 62 |

**`n400_answers`**
| field | type | notes |
|---|---|---|
| id | uuid PK | |
| question_id | int FK → n400_questions.id | |
| answer_en | text | |
| answer_vi | text | |
| is_correct | bool | true for acceptable answers, false for distractors |
| answer_audio_url | text nullable | only correct answers have audio |
| display_order | int | |

For each question: ≥1 row with `is_correct=true`, **≥5 rows with `is_correct=false` (distractors)**. At quiz time, pick 1 correct + 3 distractors → render 4 options.

**Rationale for ≥5 distractors (not 3):** the session-collision rule below filters out distractors whose text matches a correct answer of any other question in the same 20-question mock test. With only 3 distractors per question, the filter frequently leaves <3, forcing a fallback that reintroduces collisions. Authoring 5 gives the runtime headroom to enforce the rule strictly.

**Q29 (Representative) special case:** the seeded `n400_answers` rows for Q29 are the *distractor pool only* — they must be plausible non-rep names (e.g. governors of other states, fictional names "John Smith, Member of Congress", or random reps from *other* states). The correct answer is injected at quiz-build time from `n400_representatives` based on the user's resolved district. Q29 must never have an `is_correct=true` row in `n400_answers`.

**`n400_location_answers`** (Q23, 61, 62 — by state)
| field | type |
|---|---|
| id | uuid PK |
| question_id | int FK |
| state_code | text (2 char, e.g. "TX") |
| answer_en | text |
| answer_vi | text |
| answer_audio_url | text |

UNIQUE(question_id, state_code, answer_en).

**Q23 modeling rule:** USCIS Q23 is "Name **one** of your state's two U.S. Senators." Either senator is acceptable. Therefore Q23 stores **two rows per state** (one per senator), not a single combined "X and Y" string. Q61 and Q62 store one row per state (single governor / capital).

**Empty-set states:** for jurisdictions with no senators (DC, territories — out of scope v1 since we only seed 50 states), Q23 would have zero rows; quiz engine must skip Q23 for such states.

**`n400_state_data`** (static reference, 50 rows)
| field | type |
|---|---|
| state_code | text PK |
| state_name_en | text |
| state_name_vi | text |
| governor_name | text |
| capital_city | text |
| senator_1 | text |
| senator_2 | text |

**`n400_representatives`** (Q29 — by district)
| field | type |
|---|---|
| state_code | text |
| district_number | int |
| rep_name | text |
| rep_audio_url | text |

PK: (state_code, district_number).

### 3.2 User tables (RLS-scoped to user_id)

**`n400_user_profile`**
| field | type | notes |
|---|---|---|
| user_id | uuid PK FK → auth.users | |
| city | text | |
| state_code | text | |
| zipcode | text (5 digit) | |
| district_number | int nullable | resolved by Geocodio |
| district_resolved_at | timestamp nullable | |
| current_streak | int default 0 | |
| longest_streak | int default 0 | |
| last_activity_date | date nullable | user timezone (America/Chicago v1) |
| created_at | timestamp | |
| updated_at | timestamp | |

**PII minimization & third-party disclosure:** the street address is NOT persisted to our DB. It is sent **to Geocodio (a third-party API at geocod.io)** in-memory during the setup server action, used to resolve `district_number`, then discarded. To change district later, user re-enters full address.

The bilingual privacy notice on the setup form must accurately disclose this:
> "Địa chỉ đầy đủ được gửi đến Geocodio (dịch vụ tra cứu khu vực bầu cử) chỉ để xác định Hạ nghị sĩ của bạn — không lưu trữ trên hệ thống của chúng tôi. / Your full address is sent to Geocodio (a districting lookup service) solely to identify your Representative — it is not stored on our servers."

**Operational guards:**
- Geocodio is called with the API key in an `Authorization: Bearer` header, NOT as a `?api_key=...` query string (avoid leakage in any incidental logging).
- Errors thrown from `geocodeAddress` MUST NOT include the input address in the message before the catch block strips it; downstream Sentry capture must scrub the `query` field.

| passed | bool nullable (only for mock_test) |

| completed_at | timestamp nullable (null until session done) |

**`n400_question_attempts`**
| field | type |
|---|---|
| id | uuid PK |

| question_id | int FK |

| answered_at | timestamp |

### 3.3 RLS policies

Reuse existing admin pattern from `phase_b_website_tables.sql`: `profiles.role = 'admin'`. Do NOT create a new `user_roles` table.

Admin check expression (used across all admin-write policies):
```sql
EXISTS (SELECT 1 FROM public.profiles WHERE id = auth.uid() AND role = 'admin')
```

- `n400_questions`, `n400_answers`, `n400_location_answers`, `n400_state_data`, `n400_representatives`:
  - SELECT: public (anon + authenticated)
  - INSERT/UPDATE/DELETE: admin only (via expression above)
- `n400_user_profile`: user can SELECT/UPDATE/INSERT own row only (`auth.uid() = user_id`); admin can SELECT all
- `n400_quiz_attempts`, `n400_question_attempts`: user SELECT/INSERT own; admin SELECT all; no UPDATE/DELETE for users (preserve history)

**Server-side authority for sensitive writes:** Mock test `passed` boolean and final score MUST be computed server-side (Server Action) from `n400_question_attempts` rows, not from client-supplied values. Client cannot directly INSERT into `n400_quiz_attempts` with `passed=true` — that field is set only by the server action that finalizes the attempt.

**Server-side `was_correct` derivation:** the `submitAnswer` server action MUST NOT trust a client-supplied `wasCorrect` flag. It receives only `(attemptId, questionId, selectedAnswerId)` and recomputes correctness server-side by:
1. Looking up the attempt's slide manifest (cached server-side per attempt — see §4.3 "slide manifest" below) to get the set of correct answer IDs (or correct answer texts for Q29 / location questions).
2. Comparing `selectedAnswerId` against that set.
3. Inserting `n400_question_attempts` with the server-computed `was_correct`.

This closes the spoofing surface where a client could POST `wasCorrect=true` to inflate the score.

**Slide manifest:** when `startMockTest` builds the 20 slides, it persists the manifest (question_id → correct answer id set) to a server-readable store. Options: (a) write to `n400_quiz_attempts.slide_manifest jsonb`, (b) write to a sibling table `n400_attempt_slides`, or (c) recompute deterministically from a per-attempt seed. Option (a) is simplest — add a nullable `slide_manifest jsonb` column to `n400_quiz_attempts` (Phase 1).

### 3.4 Storage

Bucket `n400-audio/`: public read, admin write only.

Layout:
```
n400-audio/
  questions/q001.mp3 ... q128.mp3
  answers/q001-a001.mp3 ...
  reps/{state_code}-{district}.mp3
```

## 4. User Flows

### 4.1 First-time user
1. Visit `mannaos.com/n400app` → landing (bilingual, CTA "Bắt đầu học / Get Started")
2. Click CTA → Supabase Auth login (email / Google / Facebook)
3. After auth → check `n400_user_profile`. If missing → redirect `/n400app/setup`.
4. Setup form:
   - Heading: "Cho biết bạn đang ở đâu / Where do you live?"
   - Helper (bilingual, always visible): *"Vui lòng điền địa chỉ chính xác để app xác định đúng đáp án cho câu hỏi về Hạ nghị sĩ khu vực bạn đang sinh sống. Zipcode đôi khi chồng lên nhiều khu vực bầu cử, nên cần địa chỉ cụ thể. / Please enter your accurate address so we can identify your U.S. Representative. Zipcodes sometimes span multiple districts."*
   - Fields: Street Address, City, State (dropdown 50), Zipcode (5 digit)
   - PII notice: "Địa chỉ chỉ dùng để xác định đại biểu của bạn, không chia sẻ với bên thứ ba."
   - Submit → server action calls Geocodio → save profile with `district_number` → redirect dashboard.
5. Edit profile later via "Đổi địa chỉ" link in dashboard (re-runs Geocodio).

### 4.2 Returning user
- Login → has profile → dashboard `/n400app`.
- Dashboard:
  - Streak card prominent: 🔥 X ngày, longest Y, progress bar to next milestone (3/7/14/30/100)
  - 4 large mode cards: Daily Practice, Mock Test, Flashcards, View All 128
  - Stats: total answered, accuracy %, mock tests passed
  - **"Đổi địa chỉ / Change address" link** (small, bottom of card) → re-runs the setup form pre-filled with current city/state/zip (street empty); on submit re-runs Geocodio.

### 4.3 Mock Test (core feature)
1. Click Mock Test → confirm modal ("20 câu, cần đúng 12 để pass. Sẵn sàng?") → Start
2. Random pick 20 distinct questions from the eligible pool (128 minus any excluded due to missing location data for user's state — see §5.4)
3. **Server builds the slide manifest** (server-side, persisted to `n400_quiz_attempts.slide_manifest`):
   - For each of the 20 questions: list of correct answer IDs (and for Q29 / location questions, the correct answer text injected from `n400_representatives` / `n400_location_answers`).
   - The manifest is the source of truth for grading — client-supplied `wasCorrect` is ignored.
4. For each question render:
   - Question EN + VI
   - Auto-play question audio on load (Repeat 🔊 button)
   - 4 options = 1 random correct + 3 random distractors (shuffled)
   - **Distractor collision rules** (enforced at quiz-build time):
     - A distractor for question X must not be a correct answer to any other question that appears in the same 20-question session
     - Distractors must not duplicate any of the question's own correct answers
     - With ≥5 distractors per question (§3.1), the strict filter rarely under-supplies; if it does, the engine logs a warning and falls back to picking from the unfiltered pool of that question's distractors only.
     - When the AI seeds distractor content (one-time, pre-launch), distractors should be plausible but mutually exclusive with the correct-answer pool of related questions in the same category
   - Location-based questions: query `n400_location_answers` (Q23/61/62) or `n400_representatives` (Q29) using profile.
5. User selects → `submitAnswer({ attemptId, questionId, selectedAnswerId })` → server-side derivation:
   - Server looks up `slide_manifest` for this `(attemptId, questionId)`, computes `was_correct = selectedAnswerId ∈ correctSet`, inserts `n400_question_attempts` row.
   - Server returns `{ wasCorrect, correctAnswerIds }` so the UI can render feedback.
6. UI feedback after server response:
   - ✓/✗ color + icon (driven by server response, not client guess)
   - Auto-play correct answer audio
   - Show all acceptable correct answers (for multi-correct questions)
   - "Câu tiếp theo" button
7. Stop conditions (with 20 questions answered, math guarantees one of these always fires):
   - 12 correct reached → PASS screen with shareable certificate
   - 9 wrong reached → FAIL screen with breakdown of missed questions
8. Save `n400_quiz_attempts` (mode=`mock_test`, passed=bool) + per-question rows. **`passed` is computed by the server action that finalizes the attempt, not sent from client.**

### 4.4 Daily Practice
1. Click Daily Practice → slider 1–20 (default 10) → Start
2. Same render as Mock Test, but no early stop and no pass/fail logic. Run all N questions.
3. Final score + breakdown. Save with mode=`practice`.

### 4.5 Flashcards
1. Click Flashcards → category filter (All / specific) → Start
2. Card UI: front = question EN+VI + auto audio; "Lật thẻ 🔄" reveals all correct answers + audio
3. "Đã thuộc ✓" / "Chưa thuộc ✗" buttons → save as flashcard attempt
4. Navigation: Prev / Next

### 4.6 View All 128
- Accordion grouped by category
- **Search box (required):** debounced input that matches `question_en + question_vi + answer_en + answer_vi` substring (case-insensitive). Filters the accordion list in place.
- Click expand → all correct answers + play audio
- **Filter chip "Câu yếu của tôi" / "My weakest" (required):** server-rendered list of the user's most-missed questions, derived from a SQL aggregate over `n400_question_attempts WHERE was_correct=false` grouped by `question_id`, sorted desc, top 20. Only shown to authenticated users with ≥1 attempt.

### 4.7 Streak logic
"1 active day" = complete a session in any mode with ≥5 question interactions:
- Practice / Mock Test: ≥5 questions answered (any answer counts)
- Flashcards: ≥5 cards marked Đã thuộc / Chưa thuộc

**Day attribution rule:** the streak day is the **calendar date of `started_at`** (in `America/Chicago`), not `completed_at`. This rewards "sitting down to study" and prevents losing a streak when a session crosses midnight (e.g. start 11:55 PM, finish 12:05 AM → counts for the start day).

**Server-side flow on session completion:**
1. API receives `attempt_id` from client (no streak data sent from client)
2. Server queries `n400_question_attempts WHERE attempt_id = ?` to count actual answers
3. If count < 5 → no streak update, just mark attempt completed
4. If count ≥ 5:
   - Take `DATE(started_at AT TIME ZONE 'America/Chicago')` as `attempt_day`
   - Atomic upsert on `n400_user_profile`:
     - If `last_activity_date == attempt_day` → no-op (already counted)
     - If `last_activity_date == attempt_day - 1 day` → `current_streak += 1`, `last_activity_date = attempt_day`
     - If `last_activity_date < attempt_day - 1 day` OR null → `current_streak = 1`, `last_activity_date = attempt_day`
     - If `attempt_day < last_activity_date` (late submit of older session) → only update `current_streak` if needed for that backdated day; do not regress current streak forward
   - If `current_streak > longest_streak` → update longest

Use `UPDATE ... WHERE` guard with the previous `last_activity_date` value for idempotency under concurrent device submissions.

UI:
- Header badge `🔥 X` on every `/n400app/*` page → click for modal
- Dashboard card with progress bar to next milestone (3/7/14/30/100)
- **Today-state indicator on dashboard:**
  - If `last_activity_date == today (Chicago)` → "✅ Đã học hôm nay"
  - Else → "Bạn chưa học cho ngày hôm nay. Hãy bắt đầu ngay!" (regardless of whether the most recent session was a backdated start-time)
- Toast on streak +1
- Celebration modal at milestones 3/7/14/30/100

**Session persistence across midnight:** quiz state in localStorage MUST preserve original `started_at` ISO timestamp. If user refreshes after midnight, app resumes the same session — `started_at` is not regenerated, so day attribution stays consistent.

### 4.8 Admin (`/admin/n400`)
- List 128 questions, click to edit
- Edit form: question_en/vi, answers list (add/remove/edit correct + distractors), upload audio
- Tabs for `n400_state_data`, `n400_representatives`, `n400_location_answers` management
- Cache invalidation on save (tag-based revalidation)

## 5. Error Handling & Edge Cases

### 5.1 Geocodio
- Timeout / API down → "Không thể xác định khu vực. Vui lòng kiểm tra lại địa chỉ hoặc thử lại sau." + retry button
- Address not found → block save, ask user to recheck
- **Ambiguous result (multiple districts returned):** save profile with `district_number = null`; Q29 displays "Chưa xác định được đại biểu của bạn. Vui lòng liên hệ admin." Do NOT silently pick the first district — the parser must return null when `congressional_districts.length > 1`.
- Rate limit → save profile, mark `district_resolved_at = null`, background retry job

**Geocodio quota protection (rate limiting):**
- IP-based rate limit on `/n400app/setup` server action: 5 requests / IP / hour using Upstash Redis (already available via Vercel Marketplace).
- User-based rate limit (authenticated): 10 setup attempts per user per day.
- IP source: extract first comma-separated token from `x-forwarded-for` header (Vercel terminates and rewrites this header at the edge — trusted). Combine with `user.id` in the rate-limit key so spoofed IPs still hit per-user caps.
- On rate limit hit: 429 response with retry-after; UI shows "Quá nhiều yêu cầu. Vui lòng thử lại sau X phút."
- Reason: prevent bot abuse from exhausting the 2,500/day Geocodio free tier.
- **Auth header:** Geocodio API key is sent as `Authorization: Bearer <key>` header, never as `?api_key=` query string.

### 5.2 Audio
- File fails to load → 🔊 button disabled with tooltip "Audio đang bảo trì". Quiz continues.
- Browser autoplay blocked (iOS Safari) → Repeat button always visible, user clicks.
- Rapid question advance → stop previous audio before loading next.

### 5.3 Auth
- OAuth provider failure → email login fallback prominent
- Email unverified → redirect `/verify-email`
- Mid-quiz session expiry → save quiz state to localStorage, prompt re-login, resume.

### 5.4 Content gaps
- Missing VI translation → show EN + badge "Bản dịch đang cập nhật"
- < 3 distractors available → fall back to 2-option quiz for that question, log warning
- Missing location data for user's state → exclude that question from quiz pool, log warning
- Q29: missing rep for resolved district → "Chưa có data cho khu vực này, vui lòng liên hệ admin"

### 5.5 Quiz state persistence
- Refresh / close mid-quiz → save state to localStorage on every answer (NOT sessionStorage — must survive tab close); resume prompt on return
- The persisted state includes the slide payload AND the original `started_at` timestamp; both are keyed by `attemptId`.
- Browser back mid-quiz → unload prompt
- Mock test only saves to DB on completion (avoid skewing stats — but per-question attempts are saved as user answers, see §3.3)

### 5.6 Multi-device
- Concurrent attempts on different devices → both saved as distinct attempt rows (no conflict)
- Profile edit conflict → last-write-wins

### 5.7 Network / performance
- Slow / offline → Service Worker caches 128 questions + audio after first load. Flashcard + View All work offline. Mock Test requires online (for attempt save).
- First load > 3s → text skeleton "Đang tải câu hỏi..." (no blank spinner)

**Service Worker cache versioning:**
- API endpoint `/api/n400/content-version` returns `{ version_hash: string }` derived from latest `updated_at` across content tables (cheap query).
- SW checks `version_hash` on every navigation to `/n400app/*`; if changed → invalidate the cached question/answer responses and refetch.
- Audio files use content-hashed filenames (`q001-{hash}.mp3`) so they cache forever; admin re-upload generates new hash + updates `question_audio_url`.
- Reason: prevent stale content from being served after admin edits when user has SW cache.

### 5.8 Low-tech UX safeguards
- Buttons ≥ 48×48px
- Body ≥ 18px, questions ≥ 24px
- Confirm dialog before quitting quiz
- Bilingual error messages, no jargon
- "Trợ giúp" link on every screen

### 5.9 Admin
- Wrong audio format → reject ("Chỉ chấp nhận .mp3, max 500KB")
- Soft-delete questions referenced in attempts (preserve user history)
- Bulk import CSV → transaction rollback on failure with line numbers

## 6. Testing Strategy

### 6.1 Unit tests (critical only)
- Mock test pass/fail algorithm (12-pass / 9-fail / 20-cap)
- Question randomization: no duplicates per quiz, fair distribution
- Distractor selection: 1 correct + 3 distinct distractors, no overlap with other correct answers of same question
- Multi-correct logic: pick 1 random correct to display
- Location lookups: state→senator/governor/capital, district→rep
- Streak transitions: same-day / next-day / gap-day / multi-device idempotency

### 6.2 Integration tests
- Geocodio: mock happy path, timeout, not-found
- Auth → profile gate → setup redirect
- RLS: user A cannot read user B attempts; admin can read all
- Admin edit → cache invalidation → public reflects

### 6.3 E2E (Playwright, scoped)
- Signup → setup (Houston 77083) → dashboard
- Mock test pass golden path → certificate
- Mock test fail path → breakdown
- Flashcard flip + audio play

### 6.4 Skip (YAGNI v1)
- UI presentation tests
- Audio playback browser verification
- Admin UI E2E (manual QA sufficient)

### 6.5 Pre-launch data verification scripts
- Compare DB content vs `docs/N400_questions_en.md` and `N400_questions_vi.md` (count, ordering)
- Every question has ≥1 correct + ≥3 distractors
- Every `question_audio_url` and correct-answer `answer_audio_url` exists in Storage
- All 50 states have senator_1/2, governor, capital populated

### 6.6 Analytics events (GA4 + Meta Pixel)
- `n400_signup_complete`
- `n400_setup_complete`
- `n400_mock_test_start`
- `n400_mock_test_pass` ← high-value retargeting event
- `n400_mock_test_fail`
- `n400_practice_complete`
- `n400_flashcard_session`
- `n400_streak_milestone` (param: streak_count, fires at 3/7/14/30/100)

**Anti-spoofing for `n400_mock_test_pass`:**
- Pass/fail is computed server-side from `n400_question_attempts` rows when finalizing `n400_quiz_attempts.passed`.
- Per-question `was_correct` is also computed server-side from the persisted slide manifest (§3.3 / §4.3) — client-supplied flags are ignored. This closes the loop on score inflation.
- Server-side fires the Meta CAPI event using existing `lib/analytics/meta-capi.ts` from Phase 4 — NOT client-side Pixel for this conversion event. This prevents users from spoofing the "Pass" status to pollute the retargeting audience.
- Client-side Pixel fires non-critical events (start, milestone) for funnel visibility, but `n400_mock_test_pass` and `n400_setup_complete` (lead conversion) go through server-side CAPI only.
- **Deterministic event_id:** for retry-safety, derive `event_id = sha256(attemptId)` (for pass) and `event_id = sha256(user.id + ':setup:' + state_code + ':' + district_number)` (for setup_complete). Meta dedupes by event_id, so retries (e.g. flaky network on `finalizeAttempt`) won't double-count conversions.
- Use existing event_id pattern (`lib/analytics/events.ts`) for client-side events where dedupe with server is required; otherwise random UUIDs are fine.

### 6.7 Monitoring (ties to Track 3 W1)
- Sentry: Geocodio errors, Supabase query failures
- Uptime check on `/n400app`
- CWV alert

Rationale: rep/governor/capital names are short proper nouns that TTS pronounces poorly anyway, and skipping them halves the audio batch and storage cost. v1 still meets the "audio pronunciation helps user prepare" success criterion via the question + senator audio.
4. **Distractor strategy.** ✅ Script uses Claude API to generate ≥5 distractors per question (≥640 total), exports CSV for user review and manual edits before DB import. Q29 distractors are seeded from a curated pool of "Member of Congress" placeholders (e.g. random reps from non-user states); the actual rep is injected at quiz time from `n400_representatives`.
5. **Service Worker scope.** ✅ Registered only at `/n400app/*` scope, with content-version cache busting per §5.7.
6. **Upstash Redis.** ✅ Provision via Vercel Marketplace (free tier 10k commands/day) for Geocodio rate limiting per §5.1.
